# Parser

Парсер и аналитика access-логов nginx: лог парсится в MySQL, на `/dashboard` выводятся графики и таблица с фильтрами. Описание и запуск: `README.md`.

## Когда что читать
Читай файл перед задачей из соответствующей области.
- Версии PHP/Laravel, зависимости, команды, структура → `.claude/conventions/stack.md`
- nginx, формат и путь лога, парсер → `.claude/conventions/nginx.md`

Версии нигде не дублируй, ссылайся на `stack.md`.

## Правила и ограничения

### Процесс
- Согласование: по умолчанию любое изменение файлов требует предварительного одобрения плана или кода. Слова «применяй» / «делай» в исходном запросе считаются одобрением: показать краткий план и сразу приступить к реализации, без ожидания. Команды (`/feature`, `/task`) это правило не отменяют. Если согласованный план меняется, новые изменения согласовать повторно.
- Если при реализации выяснилось, что план ошибочен или не учитывает существующий код: не делать отклоняющихся изменений, описать противоречие и затронутые файлы, предложить минимальную корректировку и дождаться одобрения.
- Коммитит и пушит только человек; diff от ИИ всегда смотрит человек.
- В staging добавлять только новые файлы, созданные в рамках задачи, и только по конкретным путям (`git add <путь>`). Не использовать `git add .` и `git add -A`; staging существовавших файлов не менять, если это не часть задачи.
- Миграции, очистку кэша, пересоздание БД не запускать без явного разрешения.
- Работать только с локальными данными и окружением. Секреты и `.env` не читать и не коммитить.
- Если что-то неясно, спросить.
- Не выходить за рамки согласованного плана; при необходимости остановиться и спросить.
- Никогда не делать `git commit` и `git push`.
- Технически закреплено в `.claude/settings.json`: `deny` для чтения `.env*`, `git commit/push`, `git add .`/`git add -A`, `artisan migrate`; `ask` для правок nginx и docker-compose. Остальные правила здесь — указания модели, их выполнение не проверяется автоматически.

### Код
- Минимальные изменения, без рефакторинга вне задачи. Стиль: Laravel Pint.
- Слои: контроллер → сервис → репозиторий. Логика не в контроллерах и моделях.
- Зависимости ]через интерфейсы из `app/Contracts`, биндинги в `AppServiceProvider`.
- Ввод валидировать (FormRequest / `validate()`), mass assignment только через `$fillable`.
- Полные описательные имена переменных; вложенные тернарные операторы запрещены.

### База данных
- Запросы только через Eloquent / Query Builder; ввод в SQL не конкатенировать.
- N+1 избегать (`with()`); для новых фильтров и сортировок проверять индексы.
- Многошаговая запись в транзакции.
- `logs:parse` идемпотентен: повторный запуск не создаёт дублей.
- Миграции только новыми файлами, с рабочим `down()`; выпущенные не менять.

### nginx и логи
- Правки `nginx/**` и `docker-compose.yml` требуют подтверждения (`ask` в `.claude/settings.json`). Не менять `log_format`, путь лога, имя сервиса `php`, порты без согласования.
- Не добавлять в конфиг rewrite/redirect, ломающие маршрутизацию через index.php.
- Изменение формата лога требует правки `app/Services/LogParser`.

### Роли агентов и команд
- `backend-planner`, `code-reviewer`, `backend-validator` ничего не редактируют; planner не пишет код, validator не предлагает крупных рефакторингов.
- Оркестратор `/feature` сам код не пишет и файлы не редактирует, только вызывает агентов.
- `/code-analysis` только читает код и выдаёт отчёт; исправления предлагает минимальные, файлы не меняет.
- Замечание reviewer'а принимается только с подтверждением в коде (изучить окружающий код и соседние слои, например FormRequest); непроверенное предположение подаётся как гипотеза, а не как ошибка.
- Исправление считается успешным только после повторного ревью и успешной валидации, а не по отчёту implementer'а.
- Валидатор не запускает тесты против боевой БД и destructive-тесты без явного разрешения; перед запуском проверяет, на какую БД указан тестовый конфиг.

### Приоритет правил
1. Ограничения платформы и разрешения инструментов (`.claude/settings.json`).
2. `CLAUDE.md`.
3. Инструкции команды.
4. Инструкции агента.
5. Текущая задача пользователя.

Нижестоящие инструкции не отменяют вышестоящие запреты. Если два правила одного уровня противоречат друг другу, остановиться и сообщить о конфликте. Это приоритет внутри проекта, а не полная иерархия платформы.

## Работа с ИИ
- Агенты: `.claude/agents/`; команды `/feature`, `/task`, `/code-analysis`: `.claude/commands/`.
- Изменения в `.claude/`, `CLAUDE.md`, `.mcp.json` идут через обычный MR и ревью.
- Личное (язык ответов, длина объяснений, модель, звуки) живёт в `~/.claude`.
- Ошибки ИИ (выдуманный метод, пропущенная уязвимость) фиксировать в общем списке и дорабатывать по ним промпты.
